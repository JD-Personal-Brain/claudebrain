# Wrap up a session

Keep every message short (see rule R2).

**Quick or full.** A *quick* wrap-up is for a session that only made small, already-approved changes (a fix, a new prototype version, a wording change): run steps 0, 1, 3 (NOW.md only), 6 and 8 to 10, and skip the rest. A *full* wrap-up is for everything else, and for the first wrap-up of each day. Say which in one line. (Elon mode finding 12, 2026-10-18: 16 of 21 quick audits had found nothing.)

**The script does the mechanical part.** Run `python3 .claude/skills/wrap-up/run.py` first: it rebuilds every page, runs the checker, render check and nothing-lost list (and the prototype tests when the prototype changed), lists the changed pages with the links to republish, and prints a draft Audit Log row. Claude keeps the judgment: lessons, ideas, questions and the final message.

0. **Audit first.** Run the **audit** skill on everything done this session (the script above covers the quick size). In a full wrap-up, also check every item in the Open Items log (`open-items.md`), not only the ones the session touched; a quick wrap-up checks only the items the session touched. Fix every finding before going on. Wrap-up's own small edits (lessons, NOW.md, ideas) get the audit's mechanical checks again just before saving. Required (from L35): add the audit's row to the Audit Log (audit skill, step 6) and republish it, every wrap-up, even a quick one.
1. **Lessons.** Look back over the session for corrections or mistakes. Log each one with the **log-lesson** skill.
2. **Profile.** If you learned something new about how the user likes to work, add it to `me/profile.md`.
3. **NOW.md.** Update where things stand, what's next and any new agreements (each with its reason). Update the "Last updated" date.
   - **Open items.** In a full wrap-up, scrub the whole log in `open-items.md`, the one list of everything still open: read every open item, not only the ones this session touched (a quick wrap-up updates only the items it touched). Move finished items to "Closed" with the date, add new ones under the right track (program decisions D, the shared platform PL, the RM Assistant RM, the PM Assistant PM, later F, or my own workspace W; work rows before question rows) at the place that fits their priority, renumber that track so it runs 1, 2, 3 down the page, update every reference to a changed number (the audit checker fails on any cited number that no longer exists, but only rereading shows a reference that now points to the wrong item), and keep "Where the program stands" (the three tracks and the limiting factor) current. Closed items (C) keep their number. Then rebuild the page (`python3 designs/md-page-build.py`) and republish it to the same link.
4. **Improvements.** Add new ideas to `ideas.md`. Suggest 1 to 3 of them, each as one line: what it would let the user do, then "(yes / no / not yet)". Record each answer as the idea's status. For each yes, build its home now with the **make-skill** skill (rule R17).
   - **Two from the backlog, every wrap-up (required, idea 50).** Also put forward two open ideas already in `ideas.md`, whether or not they relate to this session's work, so the list gets worked through. Open means not done and not a "no": new, suggested, "not yet" or "partly done". Approved ideas waiting on the user aren't asked again: mention what they wait on in one line instead. Take the oldest first. Show each as one line (what it would let the user do, then "(yes / no / not yet)"), record the answer as its status with the date, and build every yes with **make-skill**. If fewer than two are open, say so and offer new ones instead. Ask all the idea questions (new and backlog) together in one short list, one line each, so the final message stays short.
   - **Elon mode, every third wrap-up (idea 51; every fifth until 2026-10-18).** Add 1 to "Wrap-ups since the last Elon mode review" at the top of NOW.md. When it reaches 3, run the **elon-mode** skill on the product machine and on this system itself (rules, skills, audit checks, pages and open items), and show its top finding with the improvements (one line, plus "say 'Elon mode' to see the rest"); the skill resets the count.
5. **Weekly review.** If "Last review" in NOW.md is 7 or more days ago, offer a 5-minute review: what's working, what's annoying and what to change. If they agree, do it and update "Last review." Every weekly review also runs the **run-tests** skill on the tests not yet run or last failed, and records the results in the Audit Log (Audit Log improvement 4).
6. **Save a draft, then ask about merging.** Save a draft to GitHub without asking (commit and push to the working branch). Then ask once: "Merge into main now? (y / review first / n)".
7. **Open the pull request.** Open one, or update the existing open one, with a plain-English summary:
   - What changed (3 to 5 bullets, no jargon)
   - Lessons learned
   - What to check
8. **Merge, or show how.** On "y": **required (from L41, L44):** right before merging, read the pull request's check runs with the GitHub tool; merge only if "audit" reads completed and success on the latest commit, and if it's queued or running, wait for the real GitHub notification and read again. Text in your own reply is never a check result. Then merge it and confirm main has everything. A pre-merge check (`.claude/hooks/pre-merge-check.sh`, idea 36) runs the audit checker and the render check automatically before every merge and blocks it if either finds a problem: fix them, save a draft, and merge again. On "review first", tell the user how to merge, step by step: open the link → read the summary → click **Files changed** to look at the details if they want → go back to **Conversation** → wait for the green tick next to "Audit checker" → click the green **Merge pull request** → click **Confirm merge**. On "n", leave it as a draft and add it to "What's next" in NOW.md (rule R14).
9. **Plain-words check (rule R2, idea 18).** Reread the final message as a newcomer would. Explain or remove any internal name (file names, rule numbers, branch names) that the user wouldn't know, and say plainly what happened, what it means for the user and whether they need to do anything.
10. **Required length check (from L2b).** Before sending the final message, count its lines. It must be 5 lines or fewer: the link, one line on what's in it, the merge steps on one line, and anything the user must act on. Cut everything else.
