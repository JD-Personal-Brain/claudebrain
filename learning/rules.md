# Rules

One line each. Claude follows these every session.
Rules at Level 2 or higher go at the top.

- **R23 (Level 3, automatic).** When a term, count, definition or item number changes, search the whole repo for every old form (singular, plural and the number) and fix each hit before saying it's done; when merging a branch written under older numbers, search every file it adds too, and check each item number still points to the right item. Add retired wording to the glossary's "Old wording we've retired" table, so the audit checker fails on any leftover. When a decision closes, update every page that still describes it as open or proposed (from L29). When I set a page or product name, add it to the checker's page-name check (check 11) so any other form fails, and confirm it on the rendered pages. When a new agent, control or workflow number is added, update the page kit's link pattern (`designs/pagekit.py`) in the same change and check the number links on the rendered page (from L42). Before naming or renaming a page, section or item, check each key word against `glossary.md`; if it would mean something different, choose another word or update the glossary in the same change (was R25, merged 2026-10-18). *(from L20, L21, L24, L26, L29, L42; automatic checks added with idea 37 and on 2026-10-14)*
- **R31 (Level 2).** Do exactly what I ask, and stay on my goal (merged with R3, R5 and R34 on 2026-10-18). Answer my question first and keep momentum; for setup problems, fix what you can, give me at most one step, then get back to the work. If a new detail might change the direction, ask before switching. When a decision or request implies follow-up work, don't write it into the Open Items log, NOW.md or "What's next" and don't start it; at most, mention it once, labeled **Optional**. The same goes for audit findings in pages outside the task's scope (none today: the PM pages opened on 2026-10-19): report them once as **Optional**, don't fix them. A page written for one user group's people (such as the three RM pages) talks only about that group; cross-group notes go in the detail document for AI or the shared pages, and when cutting a long file down for people, ask of each section "does this reader need it?" *(from L3, L3b, L5, L28, L34, L38)*
- **R32 (Level 2).** Never state as fact anything only the bank knows (how its people work, its data, its policies, what will hold a project up), on a page, in a plan or on a to-do list. Write it as an open question, or as "our assumption, to confirm with the bank" with the question to ask. This includes answers to review questions like "what's the limiting factor?" *(from L36, L39)*
- **R27 (Level 2).** Before building or publishing a new layout, look or structure for any page (including reorganizing an existing one), show a small sample, such as a screenshot, and get my yes. Small fixes to an approved layout don't need one. *(from L23)*
- **R22 (Level 2).** Never ask me to read or proofread reference pages (the Agent Library, Workflow Maps, Steps Catalog, Controls Catalog, Glossary or any page built to look things up). Claude keeps them in line with the working files through the audit, quietly: checks on live pages run inside the publish, never as a string of page-read prompts for me to approve. My review list holds only decisions and what I've said I'll read. *(from L18, L30)*
- **R18 (Level 3).** Nothing is offered for merging into main until it passes the **audit** skill at the size its step 0 picks (quick: the scripts; standard and deep: the scripts plus a fresh reviewer, fixes and a second reviewer). The audit is step 0 of every wrap-up. Before merging, wait until GitHub's audit check reads passed on the latest commit. *(from L15, L41)*
- **R7 (Level 3, automatic).** Check every change the way I will see it before saying it's done: for files, look at where the edit landed; for designed pages, run the render check on every page (`designs/render-check.js`: no empty tables, nothing cut off, no sideways scrolling, no stray marks, every jump link lands on its section) and look at screenshots that include the top and the bottom of each changed page. When I make an edit Claude can't (such as a settings file), Claude reads the result back right away and repairs it before calling it done. *(from L7, L7b, L7c, L7d, L19, L32)*
- **R6 (Level 3).** Never ask me for something already saved in the repo. The startup hook updates this copy from main automatically; if it warns, tell me first. Before ever saying a file is missing, check origin/main. Before describing where the program stands or proposing how to organize it, fetch main and read its NOW.md, then organize by the shared platform plus every user group served (RMs and PMs), never one group with the others as "later" unless NOW.md says so (from L43). *(from L6, L6b, L43)*
- **R2 (Level 3, automatic warning since 2026-10-17).** Write for me, short and clear (merged with R8 and R13 on 2026-10-18). Keep anything I need to review tiny: about 5 lines and one question, including the final wrap-up message and every report that ends a task: open with the outcome and what it means for me, then at most one step for me; details go in the pull request. Short must never beat clear: no shorthand, reread every message as a newcomer, say what happened, what it means for me and whether I need to do anything, and name the exact step ("save a draft" or "merge into main"), never just "save to GitHub". Every suggested or recommended action starts with a bold **Needed** or **Optional** label and a one-line reason, including answers to "should I...?" A Stop hook (`.claude/hooks/reply-length.py`) stops any reply past 8 lines and asks for a short follow-up (idea 57). *(from L2, L2b, L8, L8b, L10, L10b, L10c, L10d, L33)*
- **R16 (Level 2).** Before writing anything, decide who reads it. If a person will read it (me included: memos, plans, manuals, playbooks, summaries), deliver it as a designed, branded page from the start, without being asked; the .md is only the working copy, and if a designed version exists, update it in place. Only files that only Claude uses (rules, skills, NOW.md, logs) stay plain. *(from L13, L13b)*
- **R9.** Big tasks: before starting, write a "done" checklist, and at the end show pass or fail for each item, with proof; after each finished stage, update NOW.md with what's done and the one next step (merged with R10 on 2026-10-18). *(from ideas 9 and 10)*
- **R12.** When writing a prompt, build it from `prompting.md` (template pieces, a reason for each rule, long material first) and run its checklist before handing it over. *(from the 2026-10-09 prompting agreement)*
- **R14.** Work isn't safe until it's in main. If the startup check reports unmerged work, tell me first and offer to bring it in; at wrap-up, offer to merge right away. *(from L11)*
- **R17.** When I say yes to an idea, build its home in the same session with the **make-skill** skill: a new skill, a step in an existing skill, a rule with a test, or a one-off task on "What's next" or in the Open Items log. If there's no time, put it there right away, so an approval never sits only in `ideas.md`. *(from L14; strengthened 2026-10-09 with make-skill)*
- **R21.** Check before you claim (merged with R1, R11 and R20 on 2026-10-18). Before explaining how a tool or process works, check it first or say "I'm not certain". Before saying something follows a tip, rule or standard, check its actual wording point by point. Before writing that a step, section or file covers something, open it and find the words; if they aren't there, write "not covered yet". Before doubting a fact or writing "not public", "not found" or a guessed date, search the repo and the sources already opened, then run one search; voice the doubt only if it's still unanswered, and say where you looked. *(from L1, L9, L16, L17)*
- **R24.** When I share an outside chart, exhibit or table (a screenshot or pasted text), save it in the matching memo the same session, with every number, its labels and its source line (publisher, survey or report, date, sample size), so later plans can cite it without my pasting it again. If no memo fits, ask where it belongs. *(from idea 39)*
- **R26.** When something is wrong, fix it properly and, where possible, add a check so it can't happen again. Never leave a known error in place with a note or report it as "left on purpose"; if the real fix needs your decision, ask. And never treat a design choice Claude made as your rule: check where a rule came from before citing it. Don't retry a fix that failed unless there's a new reason to expect it to work: say what failed, why and what's different; after two failed tries, stop and tell me (was R19, merged 2026-10-18). *(from L22, idea 12)*
- **R28.** At the start of every session, check the bank news scout's last scheduled run (list the scheduled tasks). If its last run failed, stalled or is overdue, say so in the start lines with the reason; if it succeeded or hasn't run yet, say nothing. *(from idea 45)*
- **R29 (automatic).** When content moves between pages or files, list every removed line and find each one in its new home, or say it was cut on purpose and why, before review: the audit runs `lost-lines.py`, which lists every sentence that disappeared. Facts copied into a new table are checked against their source. *(from L25; automatic list added with idea 46)*
- **R30.** When I ask to connect or integrate pages, link summary to detail first: each item on a summary page links to its exact card or section on the deeper page, and related pages link to each other. Each piece of content keeps one home; suggest moving or copying content between pages only if I ask. *(from L27)*
- **R33.** When a new way of organizing a plan is agreed, rebuild the plan around one spine, opening with what the product is, instead of adding the new scheme on top of the old ones. *(from L37)*
- **R35.** Never send my email address or any personal detail to an outside website or service (a download request, a form, a search) unless I ask for that exact use; identify tools by a generic name instead. *(from L40)*
