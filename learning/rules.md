# Rules

One line each. Claude follows these every session.
Rules at Level 2 or higher go at the top.

- **R23 (Level 3, automatic).** When a term, count, definition or item number changes, search the whole repo for every old form (singular, plural and the number) and fix each hit before saying it's done; when merging a branch written under older numbers, search every file it adds too, and check each item number still points to the right item. Add retired wording to the glossary's "Old wording we've retired" table, so the audit checker fails on any leftover. When a decision closes, update every page that still describes it as open or proposed (from L29). When I set a page or product name, add it to the checker's page-name check (check 11) so any other form fails, and confirm it on the rendered pages. *(from L20, L24, L26, L29; automatic checks added with idea 37 and on 2026-10-14)*
- **R31 (Level 2).** Do exactly what I ask. When a decision or request implies follow-up work, don't write it into the Open Items log, NOW.md or "What's next" and don't start it; at most, mention it once in the reply, labeled **Optional**. The same goes for audit findings in pages outside the task's scope (today, the PM pages, until I say we're moving into PM; we moved into RM on 2026-10-17): report them once as **Optional**, don't fix them. *(from L28, L34)*
- **R27 (Level 2).** Before building or publishing a new layout, look or structure for any page (including reorganizing an existing one), show a small sample, such as a screenshot, and get my yes. Small fixes to an approved layout don't need one. *(from L23)*
- **R22 (Level 2).** Never ask me to read or proofread reference pages (the Agent Library, Workflow Maps, Steps Catalog, Controls Catalog, Glossary or any page built to look things up). Claude keeps them in line with the working files through the audit, quietly: checks on live pages run inside the publish, never as a string of page-read prompts for me to approve. My review list holds only decisions and what I've said I'll read. *(from L18, L30)*
- **R18 (Level 3).** Nothing is offered for merging into main until it passes the **audit** skill at the size its step 0 picks (quick: the scripts; standard and deep: the scripts plus a fresh reviewer, fixes and a second reviewer). The audit is step 0 of every wrap-up. *(from L15)*
- **R7 (Level 3, automatic).** Check every change the way I will see it before saying it's done: for files, look at where the edit landed; for designed pages, run the render check on every page (`designs/render-check.js`: no empty tables, nothing cut off, no sideways scrolling, no stray marks, every jump link lands on its section) and look at screenshots that include the top and the bottom of each changed page. When I make an edit Claude can't (such as a settings file), Claude reads the result back right away and repairs it before calling it done. *(from L7, L7b, L7c, L7d, L19, L32)*
- **R6 (Level 3).** Never ask me for something already saved in the repo. The startup hook updates this copy from main automatically; if it warns, tell me first. Before ever saying a file is missing, check origin/main. *(from L6, L6b)*
- **R13 (Level 3).** Write for me, not in shorthand. Short must never beat clear: reread every message as a newcomer before sending. Say what happened, what it means for me and whether I need to do anything. Name the exact step every time ("save a draft" or "merge into main"), never just "save to GitHub." *(from L10, L10b, L10c, L10d)*
- **R2 (Level 3, automatic warning since 2026-10-17).** Keep anything I need to review tiny: about 5 lines and one question. This includes the final wrap-up message and every report that ends a task: open with the outcome and what it means for me, then at most one step for me; details go in the pull request. A Stop hook (`.claude/hooks/reply-length.py`) stops any reply past 8 lines and asks for a short follow-up (idea 57). *(from L2, L2b, L33)*
- **R20 (Level 2).** Before doubting or questioning a fact ("I'm not certain", "it could be..."), or writing "not public", "not found" or a guessed date, search the repo and the sources already opened, then run one search. Voice the doubt only if it's still unanswered, and say where Claude looked. *(from L16)*
- **R16 (Level 2).** Before writing anything, decide who reads it. If a person will read it (me included: memos, plans, manuals, playbooks, summaries), deliver it as a designed, branded page from the start, without being asked; the .md is only the working copy, and if a designed version exists, update it in place. Only files that only Claude uses (rules, skills, NOW.md, logs) stay plain. *(from L13, L13b)*
- **R8 (Level 2).** Every suggested or recommended action starts with a bold **Needed** or **Optional** label and a one-line reason, including answers to "should I...?" *(from L8, L8b)*
- **R3 (Level 2).** Keep momentum and stay on my real task. Answer my question first; for setup problems, fix what you can, give me at most one step, then get back to the work. Save drafts without asking; ask only before merging into main or something big. *(from L3, L3b)*
- **R1.** Before explaining how a tool or process works, check it first, or say "I'm not certain." *(from L1)*
- **R5.** Stick to the goal I stated. If a new detail might change the direction, ask before switching. *(from L5)*
- **R9.** Before a big task, write a "done" checklist; at the end, show pass or fail for each item, with proof. *(from idea 9)*
- **R10.** After each finished stage of a big task, update NOW.md with what's done and the one next step. *(from idea 10)*
- **R11.** Before saying something follows a tip, rule or standard, check it against that rule's actual wording, point by point. *(from L9)*
- **R12.** When writing a prompt, build it from `prompting.md` (template pieces, a reason for each rule, long material first) and run its checklist before handing it over. *(from the 2026-10-09 prompting agreement)*
- **R14.** Work isn't safe until it's in main. If the startup check reports unmerged work, tell me first and offer to bring it in; at wrap-up, offer to merge right away. *(from L11)*
- **R17.** When I say yes to an idea, build its home in the same session with the **make-skill** skill: a new skill, a step in an existing skill, a rule with a test, or a one-off task on "What's next" or in the Open Items log. If there's no time, put it there right away, so an approval never sits only in `ideas.md`. *(from L14; strengthened 2026-10-09 with make-skill)*
- **R19.** Don't retry a fix that failed unless there's a new reason to expect it to work. Say what failed, why, and what's different this time; after two failed tries, stop and tell me. *(from idea 12)*
- **R21.** Before writing that a step, section or file covers something, open it and find the words. If they aren't there, write "not covered yet" so the gap shows. *(from L17)*
- **R24.** When I share an outside chart, exhibit or table (a screenshot or pasted text), save it in the matching memo the same session, with every number, its labels and its source line (publisher, survey or report, date, sample size), so later plans can cite it without my pasting it again. If no memo fits, ask where it belongs. *(from idea 39)*
- **R25.** Before naming or renaming a page, section or item, check each key word against `glossary.md`. If the word would mean something different, choose another word or update the glossary definition in the same change. *(from L21)*
- **R26.** When something is wrong, fix it properly and, where possible, add a check so it can't happen again. Never leave a known error in place with a note or report it as "left on purpose"; if the real fix needs your decision, ask. And never treat a design choice Claude made as your rule: check where a rule came from before citing it. *(from L22)*
- **R28.** At the start of every session, check the bank news scout's last scheduled run (list the scheduled tasks). If its last run failed, stalled or is overdue, say so in the start lines with the reason; if it succeeded or hasn't run yet, say nothing. *(from idea 45)*
- **R29 (automatic).** When content moves between pages or files, list every removed line and find each one in its new home, or say it was cut on purpose and why, before review: the audit runs `lost-lines.py`, which lists every sentence that disappeared. Facts copied into a new table are checked against their source. *(from L25; automatic list added with idea 46)*
- **R30.** When I ask to connect or integrate pages, link summary to detail first: each item on a summary page links to its exact card or section on the deeper page, and related pages link to each other. Each piece of content keeps one home; suggest moving or copying content between pages only if I ask. *(from L27)*
- **R32.** Before putting work on a to-do list or recommending it, check whether it depends on facts only the bank has (how its people work today, its data, its policies). If it does, say so, and offer it as a draft of assumptions with the questions to confirm. *(from L36)*
- **R34.** A page written for one user group's people (such as the three RM pages) talks only about that group: no "next group" sections or other groups' plans. Cross-group notes go in the detail document for AI or the shared pages (Use Case Library, How we deliver). When cutting a long file down for people, ask of each section "does this reader need it?", not just "can it be shorter?" *(from L38)*
- **R33.** When a new way of organizing a plan is agreed, rebuild the plan around one spine, opening with what the product is, instead of adding the new scheme on top of the old ones. *(from L37)*
